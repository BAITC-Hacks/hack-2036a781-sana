# План хакатона: EduQuest AI

## 1. Принятые предположения

- Продолжительность — 5 часов, включая подготовку демонстрации.
- Команда — три разработчика.
- Исходный репозиторий пустой.
- Организаторы пока не предоставили JSON/CSV, брендбук или гарантированный AI API.
- MVP запускается локально на одном ноутбуке.
- Полноценная авторизация не нужна: используется переключатель роли «Бизнес / Команда».
- Основное хранилище для демонстрации — in-memory repository с seed-данными; сохранение между перезапусками не является обязательным.
- Внешний AI подключается только при наличии времени и ключа. Детерминированный fallback обязателен.

Если организаторы дадут данные или обязательный стек, меняется адаптер данных, а не пользовательский сценарий.

## 2. Что именно создаём

Веб-приложение из двух связанных рабочих зон:

1. **Кабинет бизнеса** — ввод черновика, AI-уточнение, редактирование карточки, рейтинг, публикация и рассмотрение предложений.
2. **Каталог студентов** — просмотр всех опубликованных задач, сортировка и фильтры, отправка предложения.

Продуктовая идея: геймифицировать не студентов, а качество постановки задачи бизнесом. Пользователь видит, какие сведения дают баллы, и стремится довести карточку до уровня «готовая» или «приоритетная».

## 5. Параллельная работа трёх участников

### Участник 1 — Business UX

**Стартует сразу:** создаёт статические экраны на временных локальных данных, не ждёт API.

1. `BIZ-1`: форма черновика.
2. `BIZ-2`: форма уточнений.
3. `BIZ-3`: редактор карточки.
4. `BIZ-4`: визуализация рейтинга.
5. После первого API-контракта заменяет fixtures на реальные запросы.

**Конкретный результат:** путь `/business/new` доводит пользователя до подтверждённой карточки и публикации.

**Не трогает без согласования:** `lib/**`, `types/**`, catalog-компоненты.

### Участник 2 — Core/API и интегратор

**Стартует сразу:** создаёт проект, типы и контракты, затем публикует первый commit, чтобы остальные ребейзнулись.

1. Базовый scaffold и команды запуска.
2. `CORE-1` и короткая фиксация API-контрактов.
3. `CORE-2`, `CORE-3` и тесты.
4. `CORE-4`, включая prompt/fallback.
5. `CORE-5` и помощь с интеграцией UI.
6. Следит за работоспособностью `main` и готовит demo seed.

**Конкретный результат:** API покрывает весь сценарий, рейтинг детерминирован и объясним, приложение работает без внешнего ключа.

**Не трогает без необходимости:** компоненты business/catalog.

### Участник 3 — Catalog UX и QA демонстрации

**Стартует сразу:** строит каталог по согласованным типам или локальным fixtures.

1. `CAT-1`: каталог, сортировка, фильтры, уровни готовности.
2. `CAT-2`: детальная страница и отклик.
3. `CAT-3`: список предложений и статусы.
4. Готовит один стабильный demo fixture и чек-лист защиты.
5. Проводит сквозной smoke test после каждого merge.

**Конкретный результат:** опубликованная задача появляется в каталоге, получает предложение, которое бизнес может принять или отклонить.

**Не трогает без согласования:** рейтинг, AI и API-реализацию.

## 6. GitHub-процесс

### Начальная настройка

Интегратор создаёт репозиторий и первый рабочий scaffold в `main`. Остальные не создают параллельные версии `package.json` и конфигурации.

```bash
git init
git add README.md AGENTS.md docs/HACKATHON_PLAN.md
git commit -m "docs: define hackathon scope and workflow"
git branch -M main
git remote add origin <GITHUB_REPOSITORY_URL>
git push -u origin main
```

После scaffold каждый создаёт свою ветку:

```bash
git switch main
git pull --rebase origin main
git switch -c feat/business-flow   # участник 1
git switch -c feat/core-api        # участник 2
git switch -c feat/catalog-flow    # участник 3
```

### Ритм работы

- Коммит каждые 15–30 минут либо после одного законченного фрагмента.
- Push минимум каждые 30 минут и перед любой интеграционной точкой.
- Draft PR открыть после первого push, чтобы команда видела diff.
- Маленький PR объединять сразу после проверки; не держать трёхчасовые ветки.
- После каждого merge остальные выполняют `git fetch origin` и `git rebase origin/main`.
- За 45 минут до сдачи запретить архитектурные изменения; только исправления demo blocker.

### Имена коммитов

```text
feat(business): add clarification question flow
feat(rating): calculate score breakdown
feat(catalog): add readiness filters
fix(api): validate proposal deadline
test(rating): cover readiness boundaries
docs: update demo steps
```

### Как избежать конфликтов

1. У каждого участника своя файловая зона.
2. `types/index.ts` сначала меняет Core/API; изменения заранее сообщаются двум UI-разработчикам.
3. `package.json`, layout и глобальные стили редактирует интегратор.
4. Не использовать массовый auto-format на чужих файлах.
5. Общий компонент сначала обсуждается; его временную локальную версию можно держать внутри своей feature-папки.
6. Перед PR обновить ветку от `main`, а конфликт разрешать вместе с владельцем файла.

## 7. Почасовой план и интеграционные точки

### 0:00–0:20 — запуск

- согласовать название, стек, типы, API и демонстрационный пример;
- создать GitHub-репозиторий и scaffold;
- проверить `pnpm dev` на трёх компьютерах;
- распределить ветки и владельцев файлов.

**Checkpoint A:** каждый участник клонировал проект, приложение открывается, draft PR создан.

### 0:20–1:20 — независимые вертикальные части

- Участник 1: draft → вопросы → локальный editor.
- Участник 2: types → seed → rating → AI fallback.
- Участник 3: каталог → детали → локальная форма отклика.

**Checkpoint B:** три части работают отдельно на fixtures; формула рейтинга покрыта тестами.

### 1:20–2:15 — первый API и соединение

- опубликовать API tasks/analyze;
- соединить business flow с анализом и рейтингом;
- соединить каталог с repository/API;
- устранить расхождения контрактов.

**Checkpoint C:** созданная через UI карточка появляется в каталоге после публикации.

### 2:15–3:15 — отклики и решение бизнеса

- отправка предложения;
- список предложений у бизнеса;
- accept/reject;
- validation и пользовательские сообщения об ошибках.

**Checkpoint D — MVP freeze:** полностью пройти сценарий от слабого описания до принятого отклика. Всё, что не нужно для этого сценария, переносится в optional.

### 3:15–4:00 — надёжность и качество

- проверить пять seed-задач и уровни рейтинга;
- проверить пустой ввод, ошибку AI и некорректную ссылку;
- проверить сортировку и фильтры;
- запустить lint, test, build;
- исправлять только ошибки и визуальные проблемы ключевых экранов.

**Checkpoint E:** чистый clone/install/build работает, mock AI не требует интернета.

### 4:00–4:30 — полировка демонстрации

- визуально выделить score, breakdown и уровни;
- подготовить слабое описание и короткие ответы;
- проверить, что demo данные воспроизводимы;
- показать prompt и JSON в отдельном заранее открытом файле/экране.

**Checkpoint F:** полный прогон укладывается в 4 минуты, остаётся минута на объяснение ценности.

### 4:30–5:00 — сдача

- feature freeze;
- финальный merge в `main`;
- проверить README на чистом окружении;
- записать резервное видео/скриншоты, если правила позволяют;
- отправить ссылку на репозиторий;
- держать стабильный commit/tag `demo-final`.

**Финальный критерий:** ведущий защиты проходит сценарий без терминала, ручного редактирования seed и переключения на слайды.

## 9. Нужен ли собственный skill

На первые 3–4 часа отдельный skill **не нужен**: его создание и тестирование отнимет время, а основные правила уже зафиксированы в `AGENTS.md`. Skill становится полезным, только если команда действительно будет многократно поручать AI одну и ту же операцию.

Самый оправданный вариант — `hackathon-demo-audit`.

**Когда запускать:** после Checkpoint D и перед каждым demo freeze.

**Зачем:** агент одинаково проверяет обязательный сквозной сценарий, формулу рейтинга, AI fallback, seed-данные, команды запуска и README, а затем выдаёт короткий список блокеров.

**Что включить:**

```text
.codex/skills/hackathon-demo-audit/
├── SKILL.md
├── references/case-checklist.md
└── scripts/check-demo.ps1
```

- `SKILL.md`: триггер, порядок проверок, запрет расширять scope, формат отчёта P0/P1/P2;
- `case-checklist.md`: обязательные требования кейса и веса оценки;
- `check-demo.ps1`: lint/test/build и проверка наличия seed/prompt/README.

Не стоит делать skill для генерации обычных компонентов или коммитов: `AGENTS.md` и стандартные инструменты уже покрывают эти задачи. Skill следует создавать только после готового сквозного MVP.
