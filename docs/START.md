# Старт одного разработчика

Подготовка рассчитана на одного человека и пятичасовой кейс. Главная цель старта — попасть именно в репозиторий команды от платформы и не тратить время на перенос проекта перед сдачей. На 23 сентября 2026 года код Sana уже объединён в `main` командного репозитория; ниже остаётся инструкция для нового рабочего места.

PDF кейса указывает команду из 3–5 участников. Этот документ лишь планирует работу над кодом так, чтобы один разработчик мог выполнить её последовательно; проверьте отдельно, что состав команды соответствует правилам участия.

## До начала работы

- Получить от платформы точный URL командного GitHub-репозитория и проверить право чтения/записи.
- Установить и открыть Codex, войти в нужный аккаунт и связать GitHub, если это требуется выбранным способом работы.
- Проверить Python 3.11+, Git и редактор.
- Заранее установить необходимые пакеты и один раз проверить сетевой доступ к разрешённому AI API.
- Проверить вход в Codex и GitHub, активацию OpenAI API-кредитов и хранение ключа. NVIDIA Build/Brev — дополнительные ресурсы из руководства, не обязательный стек кейса; подключать только если это помогает основному сценарию.
- Зарядить ноутбук, подготовить зарядное устройство и проверить сеть площадки по правилам организаторов.
- Использовать только официальную сеть хакатона. Не включать раздачу интернета/точку доступа и не сканировать сеть; соблюдать запреты по трафику и нагрузочным проверкам.
- Хранить ключи локально; в Git отправлять только пустой `.env.example`.
- Использовать только разрешённые данные; не отправлять реальные персональные/конфиденциальные сведения в AI API. Проверить регистрацию состава команды отдельно: PDF указывает 3–5 участников, несмотря на планирование разработки одним человеком.

Не создавайте вместо командного проекта отдельный личный GitHub-репозиторий. Локальный `starter-kit` имеет отдельную подготовительную историю; для продолжения работы используйте свежий `main` командного репозитория.

## Первые 20 минут

### 0–5 минут: проверить кейс и доступ

1. Открыть PDF кейса, `AGENTS.md` и `docs/CASE_AUDIT.md`.
2. Открыть URL, выданный платформой. Если GitHub показывает 404, проверить, что вошли в правильный аккаунт и команда добавила его в репозиторий; попросить организатора/капитана подтвердить URL и права.
3. Не начинать основную разработку, пока командный remote не подтверждён.

### 5–12 минут: клонировать и понять исходное состояние

```bash
git clone https://github.com/BAITC-Hacks/hack-2036a781-sana.git
cd hack-2036a781-sana
git status --short --branch
git remote -v
git log -5 --oneline
```

Проверить, нет ли уже созданных файлов, локальных изменений и ключей. Если репозиторий содержит стартовый код, сначала понять его состояние; не копировать поверх существующих файлов весь `starter-kit`.

### 12–20 минут: согласовать и запустить основу

1. Прочитать `docs/CONTRACT.md`: поля, рейтинг, API и JSON-хранилище.
2. Записать незакрытый вопрос о подтверждённых этапах и баллах за фактический прогресс; при возможности уточнить у организаторов сразу.
3. Проверить `.gitignore`, пустой `.env.example`, `requirements.txt` и README.
4. Поднять базовое приложение, запустить health-check и зафиксировать первый осмысленный коммит.

## Правила на время хакатона

- Каждые примерно 20–30 минут проверять, что приложение запускается и текущая ветка/remote правильные.
- Сохранять содержательный Git-прогресс каждый отчётный час; сообщение коммита должно описывать готовый результат.
- Перед вызовом Codex формулировать один небольшой кусок работы: файлы, вход/выход, поведение ошибки, ограничения.
- После изменения просматривать diff, запускать уместную проверку и только затем коммитить.
- К 225-й минуте стремиться завершить полный путь от черновика до решения бизнеса.
- На 270-й минуте остановить новые функции. Дальше исправлять дефекты, README и запуск.
- Не покидать площадку более чем на 60 минут; соблюдать инструктаж по сети и безопасности.

## Если репозиторий по-прежнему недоступен

Проверить аккаунт GitHub, URL без опечаток и приглашение в команду. Страница 404 для закрытого репозитория обычно не позволяет отличить неверный URL от отсутствия доступа. Зафиксировать точную ошибку и получить подтверждение от платформы/организатора. До появления remote можно готовить план и читать контракт, но не считать локальные коммиты сданной работой.
