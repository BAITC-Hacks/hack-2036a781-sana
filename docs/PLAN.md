# План Sana для одного разработчика

## Цель и рамки

За пять часов собрать и показать работающий MVP по кейсу AI Sana: представитель бизнеса вводит черновик, получает уточняющие вопросы, проверяет и подтверждает карточку, видит рейтинг, публикует задачу; команда отправляет предложение и отчёт о прогрессе, а бизнес вручную принимает решение и подтверждает фактические этапы. Ядро MVP уже реализовано в локальной папке; осталось перенести его в доступный репозиторий платформы и пройти проверки перед сдачей.

Этот план рассчитан на одного разработчика с Codex. Роли трёх участников из старых инструкций здесь заменены последовательной работой одного человека. Это план разработки, а не изменение условия участия: PDF кейса указывает команду из 3–5 человек. Требования продукта и API-контракт при этом не упрощаются. Сначала клонируется репозиторий, выданный платформой; локальная папка `starter-kit` сама по себе не является командным репозиторием.

## Приоритеты по критериям кейса

| Критерий кейса | Баллы | Результат, который нужно показать |
| --- | ---: | --- |
| Геймификация бизнеса | 25 | Прозрачный рейтинг 0–100, семь показателей, недостающие сведения, пересчёт после редактирования, сортировка каталога по баллу |
| Сквозной сценарий | 20 | Черновик → вопросы → карточка → подтверждение → каталог → отклик → решение бизнеса |
| Качество карточки | 15 | Все поля из кейса, уместные вопросы, редактирование и ручное подтверждение |
| Каталог и отклики | 15 | Полный открытый каталог, фильтры, любое число откликов, ручной выбор/отклонение |
| AI-функция | 10 | Реальный вызов AI для анализа и/или вопросов либо сборки карточки; структурированный ответ, проверка и fallback |
| Техническое качество | 10 | Запуск по README, валидация, понятные ошибки, обработка отказа AI, чистая структура |
| Демонстрация | 5 | Целостный сценарий за пять минут на заранее подготовленном примере |

Используется шкала именно из PDF кейса. Общая шкала из командного руководства относится к другому уровню оценки и не заменяет семь критериев этого кейса.

## Что входит в MVP

### Обязательное ядро

1. Черновик бизнес-задачи со свободным вводом и темой/отраслью.
2. Анализ полноты и минимум три содержательных уточняющих вопроса.
3. Сборка редактируемой карточки из исходного текста и ответов пользователя. Неизвестные сведения остаются пустыми.
4. Явное подтверждение человеком перед публикацией.
5. Рейтинг по семи показателям с расшифровкой, отсутствующими сведениями и подсказками. Рейтинг обновляется при редактировании.
6. Каталог опубликованных задач с сортировкой по рейтингу и фильтрами по теме и уровню.
7. Отклик команды с идеей, планом, сроком и ссылкой. Низкий рейтинг не блокирует отклик; число откликов не ограничено.
8. Список откликов и ручные действия бизнеса «Выбрать» и «Отклонить». Можно выбрать одну, несколько или ни одной команды.
9. Набор синтетических данных минимального размера: пять черновиков, пять карточек, пять профилей команд и пять откликов.
10. Для принятой команды — фактический отчёт с доказательством, ручное подтверждение бизнеса и табло очков. Если сумма не подтверждена организаторами, открыто указать проектное допущение в 10 баллов.
11. README, воспроизводимый запуск, проверка основного пути, демо до пяти минут.

### Только после сквозного сценария

- Рекомендации по профилю команды — только как дополнительный взгляд на полный каталог.
- Анимация, история правок, сложная аналитика и дополнительные экраны.
- Развёртывание в интернете, если локальный запуск и сдача уже надёжны.

Не входят в объём кейса: регистрация и сложные роли, чат и уведомления, календарь, файловое хранилище, собственная ML-модель, векторная база, мобильная адаптация и полноценный проектный трекер.

## Рейтинг задачи

| Показатель | Вес | Поля |
| --- | ---: | --- |
| Контекст и потребность | 20 | `context`, `need` |
| Данные и материалы | 20 | `data_materials` |
| Ожидаемый результат | 15 | `expected_result` |
| Критерии успеха | 15 | `success_criteria` |
| Ограничения | 10 | `constraints` |
| Пользователи | 10 | `users` |
| Связь с бизнесом | 10 | `contact`, `interaction_format` |

Уровни: 0–39 — черновик; 40–69 — рабочая; 70–89 — готовая; 90–100 — приоритетная. Для двухполейных показателей контракт задаёт полное начисление за оба заполненных поля и половину веса за одно. Порог длины 15 символов из стартового набора — выбранное правило реализации, а не дословное требование PDF; держать его одинаковым в коде, тестах и README.

## Последовательность на 300 минут

| Время | Работа одного разработчика | Готовый результат / контрольная точка |
| --- | --- | --- |
| 0–20 | Открыть выданный платформой GitHub-репозиторий; проверить доступ, ветку и инструкции; клонировать его; изучить кейс, `AGENTS.md` и контракт; зафиксировать набор зависимостей и `.env.example`; первый осмысленный коммит | Код ведётся в командном репозитории; понятно, что разрешено и какие поля/API зафиксированы |
| 20–40 | Поднять минимальный FastAPI, `/api/health`, главную страницу; определить JSON-хранилище и загрузить минимальные синтетические данные; запустить приложение | Проект стартует локально, нет ключей в Git, экран и API связаны |
| 40–100 | Сделать поток «Бизнес»: черновик → реальный AI-анализ → минимум три вопроса → ответы → редактируемая карточка со всеми полями → явное подтверждение и публикация. Сразу добавить детерминированный fallback | Точка 100: карточку можно пройти от черновика до ручного подтверждения; неизвестные поля пусты |
| 100–165 | Реализовать чистый расчёт рейтинга, уровни, breakdown, missing и tips; показать всё рядом с карточкой; пересчитывать после каждого изменения; сохранять подтверждённые изменения | Точка 165: рейтинг понятен без просмотра кода и растёт при дополнении карточки |
| 165–225 | Реализовать полный каталог, сортировку и фильтры; форму отклика; список предложений; ручное принятие и отклонение. Проверить, что низкий рейтинг не скрывает задачу и не мешает отклику | Точка 225: сквозной пользовательский путь проходит в интерфейсе от черновика до решения бизнеса |
| 225–245 | Добавить отчёт принятой команды о фактическом результате, доказательство, ручное подтверждение бизнеса и табло. Сверить сумму с организаторами; пока её нет, явно показать допущение MVP в 10 баллов за этап | Очки появляются только после подтверждения; проектное допущение не выдаётся за число из PDF |
| 245–270 | Проверить валидацию, ошибки API и повреждённый/отсутствующий JSON; пройти AI-ошибку и fallback; выполнить необходимые проверки; заморозить новые функции на 270-й минуте | Нет падения на обычных ошибках; после 270 минут остаются только исправления |
| 270–285 | Довести README по фактической реализации, формуле и каталогу; указать модели, данные, зависимости, ограничения и сторонние материалы; проверить инструкции запуска | README позволяет постороннему человеку понять и запустить то, что действительно есть |
| 285–295 | Проверить свежий clone по README, `.env.example`, зависимости, данные, чистоту Git-истории и отсутствие секретов; исправить только блокирующие дефекты | Чистый запуск подтверждён, ключи и локальные файлы не опубликованы |
| 295–300 | Один раз прогнать пятиминутное демо, зафиксировать финальный коммит, отправить решение через страницу трека | Готовы ссылка, запускаемый проект, README и демонстрация |

Если организаторы подтвердят другую сумму, изменить `PROGRESS_POINTS_PER_CONFIRMED_STAGE` и соответствующий тест. До этого в интерфейсе и README называть 10 баллов проектным допущением.

## Контрольные точки и действия при отставании

| Минута | Проверка | Если не готово |
| ---: | --- | --- |
| 20 | Доступен командный репозиторий, прочитаны условия и контракт | Решить доступ до написания продукта. Нельзя откладывать перенос проекта на последний час |
| 40 | Приложение запускается | Убрать стилизацию и необязательные экраны; оставить один экран и health |
| 100 | Карточка строится после трёх вопросов и подтверждается человеком | Переключить AI на fallback, оставить реальный вызов как основной путь только если он уже работает |
| 165 | Рейтинг и breakdown видны, дополнение повышает балл | Отложить рекомендации и каталоговые украшения; закончить рейтинг |
| 225 | Каталог → отклик → решение проходит полностью | Убрать рекомендации и любые дополнительные экраны; довести ручной выбор |
| 270 | Рабочий путь не ломается на очевидной ошибке | Не добавлять функции, исправлять только критические сбои |
| 295 | Свежий clone запускается по инструкции | Удалить неработающие необязательные части, исправить README и зависимости |

Если сроки сжимаются, порядок сохранения баллов такой: рейтинг и прозрачность → полный основной сценарий → карточка и подтверждение → каталог и ручные отклики → реальный AI с fallback → надёжность и README → демонстрация. Исключённые функции не должны подменять обязательные пункты.

## Риски и обязательные проверки

| Риск | Как закрыть |
| --- | --- |
| Разрабатываем в локальном starter-kit вместо выданного репозитория | До начала работы получить доступ, клонировать URL платформы и проверять `git remote -v` |
| AI добавляет неподтверждённые факты | Строгая схема ответа; сохранять только сведения из черновика и ответов; пустые поля не заполнять догадками; показать fallback явно |
| Карточка публикуется сама | Публиковать только после явного нажатия подтверждения пользователем |
| Низкий рейтинг исключает задачу из каталога | Каталог включает все опубликованные задачи; рейтинг меняет только порядок и метку |
| Система назначает команду автоматически | Статус предложения меняется только после ручного решения бизнеса |
| Отклики искусственно ограничены | Не вводить квоту; проверить несколько откликов к одной задаче |
| JSON повреждён или отсутствует | Обработать чтение и запись безопасно, сохранить понятное сообщение и рабочий пустой список |
| Утёк API-ключ | Только `.env`, `.env` в `.gitignore`, пустой `.env.example`, проверить текущий diff и историю перед сдачей |
| Не хватает времени на прогресс команды | Уточнить обязательность и правила начисления у организаторов; отражать прогресс только после подтверждённого фактического результата |

## Правила работы с Codex и Git

- Работать в предоставленном GitHub-репозитории и вести прогресс небольшими понятными коммитами на протяжении каждого отчётного часа.
- Перед каждой задачей Codex задавать точные файлы, вход/выход, ожидаемое поведение и границы изменений. Просматривать diff и понимать сгенерированный код до коммита.
- Вести README с первого часа, но писать в нём только проверяемые факты о текущем коде.
- Не тратить время на БД, Docker, авторизацию, real-time или новые зависимости без необходимости; кейс не требует их для MVP. JSON остаётся выбранным вариантом этого starter-kit.
- Сторонние шаблоны, blueprint-ы, библиотеки и наборы данных перечислить в README. Синтетические примеры обозначить как синтетические.
- Перед сдачей убедиться, что чистый clone запускается по README и `.env` отсутствует в Git.

## Пятиминутная демонстрация

1. 0:00–0:30 — коротко обозначить проблему и решение.
2. 0:30–1:20 — ввести слабый черновик и показать минимум три AI-вопроса.
3. 1:20–2:25 — ответить на вопросы, отредактировать карточку, показать поля, которые остаются пустыми, и рост рейтинга с разбивкой.
4. 2:25–3:00 — вручную подтвердить и опубликовать задачу; показать её позицию и уровень в каталоге.
5. 3:00–3:45 — отправить отклик команды, в том числе проверить доступность задачи с низким рейтингом.
6. 3:45–4:25 — бизнес вручную принимает или отклоняет предложение; показать, что решение не автоматическое.
7. 4:25–5:00 — кратко показать архитектуру, AI/fallback, отчёт с доказательством, подтверждение фактического прогресса и табло команд.
