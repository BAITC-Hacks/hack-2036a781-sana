# Работа одного разработчика с Codex

Codex ускоряет реализацию, но разработчик отвечает за требования, логику, проверку и объяснение кода жюри. Выполняйте план в `docs/PLAN.md` по одному проверяемому шагу за раз.

## Перед каждым запросом

1. Откройте командный репозиторий, проверьте текущую ветку и `git status`.
2. Назовите точные файлы и небольшой результат задачи.
3. Укажите вход, выход, поведение при ошибке и неизменяемые правила кейса.
4. Попросите Codex не добавлять зависимости и не менять контракт без необходимости.

Шаблон:

```text
ЦЕЛЬ: [один небольшой результат]
ФАЙЛЫ: [точный список]
ВХОД И ВЫХОД: [структуры и сигнатуры из docs/CONTRACT.md]
ПОВЕДЕНИЕ: [обычный путь и ожидаемые ошибки]
ПРОВЕРКА: [команда или критерий приёмки]
ГРАНИЦЫ: соблюдай AGENTS.md; не выдумывай факты; не публикуй без подтверждения;
не скрывай низкорейтинговые задачи; не назначай команду; не меняй контракт,
не добавляй зависимостей и не редактируй несвязанные файлы.
Сначала кратко перечисли план и файлы, затем внеси изменение.
```

## Приём результата

- Сверить diff с запросом, контрактом и `AGENTS.md`.
- Проверить, что незаполненные AI-поля не заполнены выдуманными фактами.
- Убедиться, что AI fallback явно помечается как fallback.
- Проверить новые импорты и зависимости.
- Убедиться, что в diff нет `.env`, API-ключей, персональных данных и локальных путей.
- Выполнить только релевантную проверку для текущего изменения; затем посмотреть результат запуска приложения и commit.
- Если код непонятен, попросить объяснить его и пройти ключевую функцию вместе, прежде чем включать её в демо.

## Ритм работы

- Рабочий цикл: небольшая функция → просмотр diff → запуск релевантной проверки → коммит.
- Оставлять содержательный коммит в каждый отчётный час, согласно правилам хакатона.
- README пополнять после появления подтверждённой функции, а не придумывать его наперёд.
- К 225-й минуте закрыть сквозной сценарий; на 270-й минуте остановить разработку новых функций.
- Использовать вызовы AI экономно: сначала определить точные критерии и формат ответа, затем подключать модель.

## Готовые запросы

### Ревью изменений без правок

```text
Просмотри текущий diff и перечисли только проверяемые проблемы с файлом и строкой:
несоответствие кейсу, выдуманные AI-факты, непроверенный ввод, поломанный сценарий,
зависимость вне requirements.txt, секрет или неподтверждённое утверждение README.
Ничего не меняй.
```

### Минимальное исправление ошибки

```text
Вот команда и полный текст ошибки: [вставить]. Найди первопричину и предложи
минимальную правку. Не рефактори несвязанный код, не меняй публичный контракт.
После изменения перечисли файлы и способ проверки.
```

### Сверка README с репозиторием

```text
Сверь README с текущим кодом и конфигурацией. Отметь только утверждения,
которые нельзя подтвердить в репозитории, неточные команды запуска и отсутствующие
разделы: архитектура, формула рейтинга, правила каталога, проверочный сценарий,
данные/модели, ограничения и сторонние материалы. Не выдумывай недостающие факты.
```
