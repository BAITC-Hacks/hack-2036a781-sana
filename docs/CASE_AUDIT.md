# Сверка кейса AI Sana и стартового набора

## Источники и границы проверки

Сверены приложенный PDF «Единый кейс по геймификации практических заданий AI Sana», DOCX «Полное руководство команды — трек Образование», а также файлы `AGENTS.md`, `docs/CONTRACT.md`, `docs/PLAN.md`, `docs/START.md`, `docs/CHECKLIST.md`, `docs/CODEX.md`, `README.md` и три ролевых инструкции из локальной папки `starter-kit`.

PDF кейса является источником требований к продукту Sana. Общее руководство полезно для правил хакатона и подготовки, но раздел с критериями и примеры кейсов для трека «Образование» не подменяют конкретный кейс по геймификации. Просьба владельца проекта работать пока одному меняет способ исполнения, а не требования кейса.

Состояние на 23 сентября 2026 года: репозиторий `https://github.com/BAITC-Hacks/hack-2036a781-sana` доступен через подключённый GitHub, а проверенный код Sana находится в `main`. Подготовительные коммиты из локального `starter-kit` перенесены через pull request #1, а доработки рабочего сценария — через pull request #2; оба объединены. Локальная история `starter-kit` отличается от истории удалённого `main`, хотя код приложения и документация совпадают по содержимому. Для следующих изменений следует начать с актуального `main` командного репозитория.

## Требования конкретного кейса

### Пользовательский сценарий

1. Представитель бизнеса вводит черновик.
2. Система определяет пробелы и задаёт не менее трёх уместных вопросов.
3. Из введённых фактов и ответов формируется редактируемая карточка, которую человек подтверждает.
4. Система показывает рейтинг 0–100, его расшифровку, недостающие сведения и пересчитывает рейтинг после подтверждённых дополнений.
5. Подтверждённая задача попадает в общий каталог на место, связанное с рейтингом.
6. Любая команда просматривает задачи и подаёт идею решения, план, срок и ссылку на прототип.
7. Бизнес вручную принимает, отклоняет, выбирает несколько предложений или не выбирает ни одного.
8. Кейс отдельно упоминает баллы выбранной команде за фактический прогресс после подтверждённого этапа.

### Карточка и рейтинг

Карточка включает: название, контекст, потребность, пользователей, данные и материалы, ограничения, ожидаемый результат, критерии успеха, контакт и формат взаимодействия.

| Показатель | Вес | Поля |
| --- | ---: | --- |
| Контекст и потребность | 20 | Контекст, потребность |
| Данные и материалы | 20 | Данные/материалы |
| Ожидаемый результат | 15 | Ожидаемый результат |
| Критерии успеха | 15 | Критерии успеха |
| Ограничения | 10 | Ограничения |
| Пользователи | 10 | Пользователи |
| Связь с бизнесом | 10 | Контакт, формат взаимодействия |

Уровни готовности: 0–39 — черновик, 40–69 — рабочая, 70–89 — готовая, 90–100 — приоритетная. Низкий рейтинг не скрывает опубликованную задачу и не запрещает отклик. Рейтинг влияет на позицию и метку.

## Результат сверки стартового набора

### Что уже согласовано с кейсом

- Контракт содержит все поля карточки и семь показателей рейтинга.
- Зафиксированы уровни, структура разбивки, список недостающих полей и подсказки.
- Каталог не ограничен минимальным рейтингом; отклики принимаются независимо от балла.
- Решение по предложению предполагается только ручным действием бизнеса.
- AI-fallback допустим, если виден пользователю и не выдумывает факты.
- Есть требование минимального набора из пяти черновиков, пяти карточек, пяти профилей команд и пяти откликов.
- В отдельных синтетических JSON-файлах есть 5 черновиков, 5 карточек, 5 профилей, 5 откликов. Пять карточек с оценками 20, 65, 100, 45 и 85 охватывают четыре уровня готовности. В живой каталог примеры не загружаются.
- README заранее предусматривает архитектуру, запуск, формулу, правила каталога и проверочные сценарии.

### Несовпадения и пробелы

| Наблюдение | Почему важно | Решение в подготовленных планах |
| --- | --- | --- |
| `docs/PLAN.md`, `docs/START.md`, `docs/INDEX.md`, `docs/CODEX.md` и `docs/CHECKLIST.md` рассчитаны на трёх разработчиков | Пользователь планирует разработку одним исполнителем; последовательность и контроль времени должны соответствовать одному человеку. При этом PDF кейса указывает состав команды 3–5 участников | Переписаны как единый маршрут разработки для одного исполнителя и Codex. Это не отменяет требования кейса к официальному составу команды |
| В DOCX есть другая общая шкала критериев | Можно неправильно распределить время и оформить README с неверными баллами | При планировании использовать шкалу из PDF кейса: 25/20/15/15/10/10/5 |
| В кейсе есть пункт о баллах за фактический прогресс после подтверждённого этапа, но нет суммы и схемы этапа | Точное количество баллов нельзя приписать организаторам | Реализован проверяемый MVP: команда принятого отклика прикладывает факт и доказательство; бизнес подтверждает отчёт; табло начисляет 10 баллов за подтверждённый этап. Сумма обозначена как проектное допущение; следует уточнить у организаторов |
| README раньше описывал функции как планы, несмотря на уже написанный MVP-код | Нельзя понять, что реально готово | README обновлён по текущей реализации и указывает ограничения, fallback и допущение по очкам |
| `AGENTS.md` ранее называл базу данных прямо запрещённой кейсом | PDF не запрещает обычную базу данных; он говорит, что собственная ML-модель и векторная база не требуются в пятичасовом объёме | Исправлено: JSON зафиксирован как простое проектное решение starter-kit, а не как запрет организаторов |
| `docs/CONTRACT.md` допускает HTTP 200 и ошибки в теле для всех API | Это внутреннее проектное решение, а не требование PDF; оно может ухудшить стандартное поведение API/тестов | Не менять без необходимости; проверить фактическую ясность ошибок, UI и сценариев |
| Порог 15 символов для заполненного поля отсутствует в PDF | Это допустимое правило реализации, но его нельзя выдавать за правило организаторов | Оставить только если подтверждён одинаковыми функцией, тестами и README |
| В `data/tasks.json` у всех опубликованных карточек изначально стояли `score=0` и пустая разбивка | Каталог мог показывать неправильный уровень до пересчёта; примерные уровни не соответствовали заполненным полям | Рейтинги, разбивки, недостающие показатели и подсказки синхронизированы с карточками; примеры охватывают четыре уровня |
| Карточка подтверждается, затем публикуется, но контент может быть отредактирован перед отправкой | Нужно исключить автопубликацию и считать сохранённый рейтинг актуальным | UI должен явно выполнять публикацию только по нажатию; рейтинг на сервере пересчитывается при сохранении |
| Локальная папка изначально не была связана с URL платформенного GitHub | Работа вне командного репозитория создавала риск сдачи не туда | `origin` настроен на командный URL; код объединён в `main` через PR #1 и PR #2. Следующие изменения начинать с свежего `main` |

## Границы подготовки и следующий старт

В `main` реализован рабочий Sana MVP: AI-анализ с fallback, карточка, рейтинг, каталог, предложения, ручной выбор бизнеса и подтверждаемый прогресс команд. Проверены 22 автоматических сценария, реальный ответ OpenAI и полный путь в мобильном браузере. Чистый локальный клон установил зависимости в новом окружении, запустил приложение и прошёл 22 теста. До сдачи остаются уточнение у организаторов размера прогресс-очков, проверка состава команды по правилам PDF, пятиминутная репетиция и отправка решения через страницу трека. Общие критерии DOCX не подменяют требования конкретного PDF-кейса.

Первое действие при возобновлении: проверить URL репозитория, права записи, текущую ветку и существующий код. Затем пройти `docs/START.md`, открыть `docs/PLAN.md` и зафиксировать исходный коммит.
